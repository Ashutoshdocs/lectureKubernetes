# Kubernetes Events & Field Selectors — Teaching Notes

## 1. Kubernetes Events

Kubernetes **Events** are short-lived records generated by Kubernetes objects and controllers to explain what is happening in the cluster.

They are especially useful for troubleshooting:

- Pod creation/deletion
- Scheduling problems
- Image pull failures
- Failed readiness/liveness probes
- Container crashes and restart-related issues
- Volume mounting problems
- Node-related problems
- Other controller or cluster activity

> **Important:** Events are primarily a troubleshooting/audit-style signal, not a permanent application log.

---

## 2. View Events

### All events in the current namespace

```bash
kubectl get events
```

This normally shows events from the namespace in your current kubectl context.

Typical columns include:

```text
LAST SEEN   TYPE     REASON    OBJECT       MESSAGE
```

Example:

```text
LAST SEEN   TYPE     REASON     OBJECT          MESSAGE
10s         Normal   Scheduled  pod/event-pod   Successfully assigned default/event-pod to node01
8s          Normal   Pulling    pod/event-pod   Pulling image "nginx"
5s          Normal   Pulled     pod/event-pod   Successfully pulled image "nginx"
```

---

## 3. Generate an Event

Create a test Pod:

```bash
kubectl run event-pod --image=nginx
```

Then check events:

```bash
kubectl get events
```

You should see events associated with the Pod lifecycle, depending on the Kubernetes version and what happens in the cluster.

A useful teaching flow is:

```text
Create Pod
   ↓
Scheduler selects a node
   ↓
Kubelet starts pulling image
   ↓
Container starts
   ↓
Controllers / kubelet generate events
   ↓
kubectl get events
```

---

# 4. Namespace Matters

Events are namespaced resources.

### Events in `kube-system`

```bash
kubectl get events -n kube-system
```

This is useful when troubleshooting system components such as:

- CoreDNS
- kube-proxy
- CNI/networking components
- Other system Pods

### Events in `default`

```bash
kubectl get events -n default
```

This shows events for objects in the `default` namespace.

### Teaching point

If you run:

```bash
kubectl get events
```

you are **not necessarily seeing events from the entire cluster**.

You are querying the current namespace.

To inspect events across namespaces, use:

```bash
kubectl get events -A
```

or:

```bash
kubectl get events --all-namespaces
```

---

# 5. Event Retention — `--event-ttl`

Kubernetes API server has an event retention setting.

Edit the API server static Pod manifest:

```bash
vim /etc/kubernetes/manifests/kube-apiserver.yaml
```

Add:

```yaml
- --event-ttl=24h0m0s
```

This means events are retained for approximately **24 hours**.

### Concept

```text
Event generated
      ↓
Stored by Kubernetes
      ↓
Available to kubectl get events
      ↓
TTL expires
      ↓
Old event is removed
```

### Important

Events are **not intended to be a long-term historical log**.

For long-term observability, use appropriate logging/monitoring/auditing systems.

# 6. Understanding `--field-selector`

`--field-selector` lets you filter Kubernetes resources based on their fields.

General syntax:

```bash
kubectl get <resource> --field-selector=<field>=<value>
```

Multiple conditions can be combined with commas:

```bash
kubectl get <resource> \
  --field-selector=<field1>=<value1>,<field2>=<value2>
```

Think of it as:

```text
kubectl get resource
        +
field-based filtering
        ↓
only matching objects
```

---

# 7. Field Selectors for Events

## Find events for a specific object

```bash
kubectl get events \
  --field-selector involvedObject.name=test
```

This asks:

> "Show events where the involved object's name is `test`."

---

## Find events involving Pods

```bash
kubectl get events \
  --field-selector involvedObject.kind=Pod
```

This asks:

> "Show only events whose involved object is a Pod."

---

## Combine selectors

```bash
kubectl get events \
  --field-selector=involvedObject.kind=Pod,involvedObject.name=test
```

This means:

```text
involvedObject.kind = Pod
            AND
involvedObject.name = test
```

So the result is limited to events for the Pod named `test`.

---

# 8. Why Field Selectors Are Useful

Without filtering:

```bash
kubectl get events
```

you may get many events.

With a selector:

```bash
kubectl get events \
  --field-selector involvedObject.name=my-pod
```

you narrow the output to what you care about.

### Troubleshooting pattern

```text
Something is wrong with my-pod
             ↓
Find its events
             ↓
kubectl get events \
  --field-selector involvedObject.name=my-pod
             ↓
Look at REASON + MESSAGE
             ↓
Identify the problem
```

---

# 9. Field Selectors for Pods

Field selectors are not limited to Events.

They can also filter Pods.

## Pods in Running phase

```bash
kubectl get pods \
  --field-selector=status.phase=Running
```

Meaning:

> Show Pods whose `status.phase` is `Running`.

---

## Find a Pod by name

```bash
kubectl get pods \
  --field-selector=metadata.name=my-pod
```

Meaning:

> Show the Pod whose metadata name is `my-pod`.

For one Pod, the simpler command is often:

```bash
kubectl get pod my-pod
```

But the field-selector example is useful for teaching how selectors work.

---

# 10. Find Pods Running on a Specific Node

```bash
kubectl get pods \
  --field-selector=spec.nodeName=my-node
```

Meaning:

> Show Pods whose `spec.nodeName` is `my-node`.

This is very useful when troubleshooting a node.

---

# 11. Search Across All Namespaces

Add:

```bash
--all-namespaces
```

or:

```bash
-A
```

Example:

```bash
kubectl get pods --all-namespaces \
  --field-selector spec.nodeName=node01
```

Meaning:

> Show Pods from every namespace that are assigned to `node01`.

Equivalent shorter form:

```bash
kubectl get pods -A \
  --field-selector spec.nodeName=node01
```

---

# 12. Find All Running Pods Across the Cluster

```bash
kubectl get pods \
  --all-namespaces \
  --field-selector status.phase=Running
```

This answers:

> "Which Pods are currently in the Running phase across all namespaces?"

---

# 13. Find All Pending Pods

```bash
kubectl get pods \
  --all-namespaces \
  --field-selector status.phase=Pending
```

This is particularly useful for troubleshooting scheduling problems.

For example:

```text
Pending Pod
    ↓
Check events
    ↓
kubectl get events -n <namespace>
    ↓
Look for FailedScheduling
    ↓
Understand why scheduler could not place it
```

---

# 14. Find Pods That Are Not Running

Another common technique is:

```bash
kubectl get pods --all-namespaces --no-headers | grep -v "Running"
```

### What happens here?

`--no-headers` removes the table header.

Then:

```bash
grep -v "Running"
```

means:

> Show lines that do NOT contain the word `Running`.

So this can quickly expose Pods whose displayed status is something other than Running.

### Important distinction

This is **text filtering**, not a Kubernetes field selector.

Compare:

```bash
--field-selector status.phase=Pending
```

with:

```bash
grep -v "Running"
```

The first asks Kubernetes for objects matching a field.

The second gets command output and filters the displayed text.

For reliable scripting, prefer Kubernetes selectors when the required field is supported.

---

# 15. Combine Multiple Pod Field Selectors

Example:

```bash
kubectl get pods \
  --field-selector=spec.nodeName=node01,status.phase=Running
```

This means:

```text
spec.nodeName = node01
          AND
status.phase = Running
```

Result:

> Show Pods that are Running AND assigned to node01.

Think of:

```bash
--field-selector
```

as a database-style filter.

Imagine the cluster contains:

```text

db-1       Running    node01
```

Query:

```bash
kubectl get pods \
  --field-selector=spec.nodeName=node01
```

Conceptually returns:

```text

db-1
```

Query:

```bash
kubectl get pods \
  --field-selector=status.phase=Running
```

Conceptually returns:

```text
web-1
api-1
db-1
```

Query:

```bash
kubectl get pods \
  --field-selector=spec.nodeName=node01,status.phase=Running
```

Conceptually returns:


# 17. Events vs Pods — Same Idea, Different Fields

## Events

Commonly useful fields:

```text
involvedObject.name
involvedObject.kind
```

Example:

```bash
kubectl get events \
  --field-selector=involvedObject.kind=Pod
```

## Pods

Useful fields include:

```text
metadata.name
status.phase
spec.nodeName
```

Examples:

```bash
kubectl get pods \
  --field-selector=metadata.name=my-pod
```

```bash
kubectl get pods \
  --field-selector=status.phase=Running
```

```bash
kubectl get pods \
  --field-selector=spec.nodeName=node01
```

# 18. Troubleshooting Workflow

## Scenario: Pod is stuck

Start with:

```bash
kubectl get pods
```

If the Pod is Pending:

```bash
kubectl get pods \
  --field-selector=status.phase=Pending
```

Then inspect events:

```bash
kubectl get events
```

Or focus on the Pod:

```bash
kubectl get events \
  --field-selector=involvedObject.name=my-pod
```

Look for reasons such as:

```text
FailedScheduling
FailedMount
Failed
FailedCreate
BackOff
ErrImagePull
ImagePullBackOff
```

Then investigate the specific cause.

---

# 19. Troubleshooting by Node

Suppose `node01` has a problem.

Find its Pods:

```bash
kubectl get pods -A \
  --field-selector=spec.nodeName=node01
```

Find only Running Pods:

```bash
kubectl get pods -A \
  --field-selector=spec.nodeName=node01,status.phase=Running
```

Then inspect relevant namespace events:

```bash
kubectl get events -A
```

This creates a useful troubleshooting chain:

```text
NODE PROBLEM
     ↓
Which Pods are on the node?
     ↓
kubectl get pods -A \
  --field-selector=spec.nodeName=node01
     ↓
Which Pods are affected?
     ↓
Inspect Events
     ↓
Find Reason + Message
     ↓
Investigate root cause
```

# 21. Important Teaching Notes

### Event ≠ Log

Events tell you about **important Kubernetes state/activity changes**.

Application logs tell you what an application process is printing.

Use:

```bash
kubectl logs <pod>
```

for container/application logs.

Use:

```bash
kubectl get events
```

for Kubernetes events.

---

### Event TTL ≠ Event generation

`--event-ttl` controls approximately **how long events are retained**.

It does not mean Kubernetes only generates events for that duration.

---

### Namespace matters

These are different queries:

```bash
kubectl get events
```

and:

```bash
kubectl get events -A
```

The first is namespace-scoped.

The second searches across namespaces.

---

### Field selector ≠ label selector

Field selector:

```bash
--field-selector=status.phase=Running
```

filters by an object's **fields**.

Label selector:

```bash
-l app=nginx
```

filters by **labels**.

They solve different problems.


# 23. Key Takeaway

```text
kubectl get events
        ↓
What happened?

--field-selector
        ↓
Show only objects matching specific fields

Events
        ↓
Troubleshoot Kubernetes activity

Pod field selectors
        ↓
Find Pods by phase / node / metadata

-A
        ↓
Search across all namespaces

--event-ttl
        ↓
Control how long Events are retained
```

### Remember

> **Events answer: "What happened?"**

> **Field selectors answer: "Which objects match this condition?"**

Together, they are extremely useful for Kubernetes troubleshooting.
