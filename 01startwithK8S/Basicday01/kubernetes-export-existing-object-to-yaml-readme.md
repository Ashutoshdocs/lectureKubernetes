# Export an Existing Kubernetes Object to YAML

This guide teaches how to take an **existing Kubernetes object that is already running/existing in the cluster** and create a YAML file from it.

This is an important Kubernetes administration and troubleshooting skill.

---

# 1. The Basic Idea

Suppose Kubernetes already has this Pod:

```text
Kubernetes Cluster
        │
        ▼
      nginx
       Pod
        │
        │  already exists
        ▼
kubectl get pod nginx
```

We can ask the Kubernetes API server:

> "Give me the current YAML representation of this object."

Command:

```bash
kubectl get pod nginx -o yaml
```

We can redirect the output to a file:

```bash
kubectl get pod nginx -o yaml > nginx.yaml
```

Now we have:

```text
Existing Pod
     │
     ▼
kubectl get pod nginx -o yaml
     │
     ▼
YAML output
     │
     ▼
nginx.yaml
```

---

# 2. The General Syntax

```bash
kubectl get <resource> <name> -o yaml > <filename>.yaml
```

For example:

```bash
kubectl get pod nginx -o yaml > nginx.yaml
```

Break it down:

```text
kubectl
   ↓
get
   ↓
pod
   ↓
nginx
   ↓
-o yaml
   ↓
output the object as YAML
   ↓
>
redirect output to a file
   ↓
nginx.yaml
```

# 3. Example — Existing Pod

First check the Pods:

```bash
kubectl get pods
```

Example:

```text
NAME    READY   STATUS    RESTARTS   AGE
nginx   1/1     Running   0          10m
```

Now export it:

```bash
kubectl get pod nginx -o yaml > nginx.yaml
```

Check the file:

```bash
cat nginx.yaml
```

Or:

```bash
less nginx.yaml
```

---

# 4. Why Is This Useful?

Exporting an existing object to YAML is useful when you want to:

- Understand how an object is configured
- Inspect the complete object
- Learn Kubernetes YAML structure
- Troubleshoot an object
- Create a starting point for another manifest
- Compare an object with another object
- Save a snapshot of the object's current definition
- Recover configuration information
- Study fields generated by Kubernetes

For teaching Kubernetes, this is particularly useful because you can:

```text
Create object
     ↓
Inspect object
     ↓
Export YAML
     ↓
Study YAML
     ↓
Understand Kubernetes API structure
```

# 5. `-o yaml` Means "Output as YAML"

The `-o` option means:

```text
output format
```

Example:

```bash
kubectl get pod nginx -o yaml
```

Other commonly used output formats include:

```bash
kubectl get pod nginx -o wide
```

```bash
kubectl get pod nginx -o json
```

```bash
kubectl get pod nginx -o name
```

```bash
kubectl get pod nginx -o yaml
```

For this lesson, the important one is:

```bash
-o yaml
```

---

# 6. Redirect the Output to a File

The `>` is a shell redirection operator.

Example:

```bash
kubectl get pod nginx -o yaml > nginx.yaml
```

It means:

```text
kubectl output
      ↓
instead of displaying on screen
      ↓
write into nginx.yaml
```

Without `>`:

```bash
kubectl get pod nginx -o yaml
```

the YAML appears in the terminal.

With `>`:

```bash
kubectl get pod nginx -o yaml > nginx.yaml
```

the YAML is written to a file.

# 10. Export a Secret

```bash
kubectl get secret my-secret -o yaml > my-secret.yaml
```

## Important Security Warning

Secret objects can contain sensitive information.

Even though Kubernetes Secret data is commonly Base64-encoded, **Base64 is not encryption**.

Therefore:

```bash
kubectl get secret my-secret -o yaml > my-secret.yaml
```

should be treated carefully.

Do not casually commit exported Secret YAML to Git.

# 11. Export an Object from Another Namespace

If the object is not in the current namespace, specify the namespace:

```bash
kubectl get pod nginx -n dev -o yaml > nginx.yaml
```

General form:

```bash
kubectl get <resource> <name> \
  -n <namespace> \
  -o yaml > object.yaml
```

Example:

```bash
kubectl get deployment web \
  -n production \
  -o yaml > web.yaml
```

# 15. What Does the Exported YAML Look Like?

Suppose we have:

```bash
kubectl run nginx --image=nginx
```

Then:

```bash
kubectl get pod nginx -o yaml
```

will contain sections similar to:

```yaml
apiVersion: v1
kind: Pod

metadata:
  name: nginx
  namespace: default
  labels:
    run: nginx

spec:
  containers:
    - name: nginx
      image: nginx
```

But a live object contains more information than the original configuration.

You may also see:

```yaml
metadata:
  creationTimestamp: ...
  resourceVersion: ...
  uid: ...

status:
  phase: Running
  podIP: ...
  hostIP: ...
```

---

# 16. Very Important — Live Object vs Manifest

This is one of the most important concepts in this lesson.

When you run:

```bash
kubectl get pod nginx -o yaml
```

you are not necessarily getting the exact YAML that someone originally wrote.

You are getting the **current representation of the object stored/returned by the Kubernetes API**.

Think:

```text
Original YAML
     ↓
kubectl apply
     ↓
Kubernetes API Server
     ↓
Controllers / Scheduler / Kubelet
     ↓
Object changes over time
     ↓
Current live object
     ↓
kubectl get -o yaml
```

Therefore:

```bash
kubectl get pod nginx -o yaml
```

shows the object's current state and metadata, not simply the original hand-written manifest.

---

# 17. Configuration vs Current State

A Kubernetes object generally contains two important ideas:

```text
Object
 ├── metadata
 ├── spec
 └── status
```

## `spec`

Represents the desired configuration.

Example:

```yaml
spec:
  containers:
    - name: nginx
      image: nginx
```

Think:

> "What should Kubernetes run?"

---

## `status`

Represents the current observed state.

Example:

```yaml
status:
  phase: Running
```

Think:

> "What is happening right now?"

---

# 18. Why `status` Matters

Suppose:

```yaml
status:
  phase: Running
```

That information is generated by Kubernetes.

You normally do **not** write:

```yaml
status:
  phase: Running
```

in your application manifest.

Instead, Kubernetes determines it.

Conceptually:

```text
You specify:
    spec
      ↓
Kubernetes processes it
      ↓
Kubernetes updates:
    status
```

---

# 19. Server-Generated Metadata

A live exported object may contain fields such as:

```yaml
metadata:
  creationTimestamp: ...
  resourceVersion: ...
  uid: ...
```

These are generally managed by Kubernetes.

Examples:

### `uid`

Unique identifier assigned to the object.

### `resourceVersion`

Used internally by Kubernetes for tracking object versions/concurrency.

### `creationTimestamp`

Time at which the object was created.

### `managedFields`

Information about which actors/field managers have managed fields of the object.

These fields are useful for inspecting a live object but are usually not what you want in a clean reusable manifest.

---

# 20. Can I Directly Reuse Exported YAML?

Sometimes you can use exported YAML as a starting point, but **do not blindly assume that a live exported object is a clean manifest**.

For example:

```bash
kubectl get pod nginx -o yaml > nginx.yaml
```

Then:

```bash
kubectl apply -f nginx.yaml
```

may not be what you actually want.

The exported file can contain:

```text
status
uid
resourceVersion
creationTimestamp
managedFields
runtime-generated values
```

Some fields are server-managed and should generally be removed when creating a clean reusable manifest.

---

# 21. Clean Manifest Concept

For a reusable manifest, focus on fields such as:

```yaml
apiVersion:
kind:

metadata:
  name:
  namespace:
  labels:

spec:
  ...
```

For example:

```yaml
apiVersion: v1
kind: Pod

metadata:
  name: nginx-copy
  labels:
    app: nginx

spec:
  containers:
    - name: nginx
      image: nginx
```

Notice that we don't manually specify:

```yaml
status:
```

or:

```yaml
metadata:
  uid:
  resourceVersion:
  creationTimestamp:
```

---

# 22. Change the Name Before Creating a Copy

Suppose the original object is:

```text
nginx
```

You export:

```bash
kubectl get pod nginx -o yaml > nginx.yaml
```

If you want to create another Pod from that YAML, you cannot normally create another object with the same name in the same namespace.

Change:

```yaml
metadata:
  name: nginx
```

to:

```yaml
metadata:
  name: nginx-copy
```

Then clean any inappropriate server-generated fields.

Apply:

```bash
kubectl apply -f nginx.yaml
```

# 24. Inspect Without Saving

Sometimes you don't need a file.

Simply:

```bash
kubectl get pod original-pod -o yaml
```

This is useful when you only want to inspect a particular field.

For example:

```bash
kubectl get pod original-pod \
  -o jsonpath='{.spec.containers[*].image}'
```

This returns the container image.

---

# 25. YAML vs JSON

Kubernetes can return JSON:

```bash
kubectl get pod nginx -o json
```

or YAML:

```bash
kubectl get pod nginx -o yaml
```

YAML is generally easier for humans to read and edit.

JSON is often useful for:

- Scripts
- JSONPath
- Programmatic processing
- APIs

---

# 26. `kubectl get` vs `kubectl describe` vs `-o yaml`

These commands have different purposes.

## Quick status

```bash
kubectl get pod nginx
```

Use when you want:

> "What is the high-level status?"

---

## Troubleshooting information

```bash
kubectl describe pod nginx
```

Use when you want:

> "Give me detailed, human-friendly information and events."

---

## Complete API representation

```bash
kubectl get pod nginx -o yaml
```

Use when you want:

> "Show me the object's YAML representation."

Mental model:

```text
get
 ↓
quick view

describe
 ↓
human-friendly detailed investigation

get -o yaml
 ↓
object representation
```

# 28. A Useful Real-World Workflow

Suppose you find a running Deployment and want to understand it.

### Step 1 — Find it

```bash
kubectl get deployments
```

### Step 2 — Inspect it

```bash
kubectl describe deployment <name>
```

### Step 3 — Export it

```bash
kubectl get deployment <name> -o yaml > deployment.yaml
```

### Step 4 — Read the YAML

```bash
less deployment.yaml
```

### Step 5 — Identify the desired configuration

Look mainly at:

```yaml
spec:
```

### Step 6 — Identify generated/runtime information

Look for:

```yaml
status:
```

and generated metadata.

### Step 7 — Create a clean reusable manifest

Copy the relevant configuration into a new YAML file and remove server-generated/runtime fields.

# 32. Key Takeaways

Remember these four ideas:

### 1. Existing object → YAML

```bash
kubectl get <resource> <name> -o yaml
```

### 2. YAML → file

```bash
kubectl get <resource> <name> -o yaml > object.yaml
```

### 3. Live YAML contains more than your original manifest

It can include:

```text
metadata
spec
status
server-generated fields
runtime information
```

### 4. Exported YAML is not automatically a clean reusable manifest

Before reusing it, understand and remove/adjust fields that are generated or tied to the original object.

# 33. One-Line Memory Trick

> **`kubectl get <object> -o yaml` = "Show me what Kubernetes currently knows about this object in YAML form."**

And:

> **`>` = "Save that output into a file."**

So:

```bash
kubectl get pod nginx -o yaml > nginx.yaml
```

means:

```text
Get existing nginx Pod
        ↓
Ask API server for YAML
        ↓
Redirect YAML output
        ↓
Save as nginx.yaml
```
